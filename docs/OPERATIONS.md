# 運用・復旧手順

本書は実施手順です。監視契約、バックアップ保管先、公開DB、連絡窓口は未設定です。販売前に担当者と実行環境を決め、公開環境で一度リハーサルしてください。

## 監視と容量

- 生存監視は `/api/health`、利用可能性の監視は `/api/ready`。後者の200がDB接続・スキーマ準備完了を意味します。503は `Retry-After` を返します。DB異常だけを理由にアプリを再起動し続けないでください。
- 最初の運用目安は外形監視30秒間隔、連続3回の失敗を担当へ通知。サービスの月間可用性99.9%、既存イベント参照のp95 1秒未満を内部目標とします。これは未計測の目標で、SLAではありません。
- 通常は各参加者が3.5〜3.75秒間隔で参照します。300人で約83リクエスト/秒に加え、幹事・投影・新規参加分が必要です。Freeの10リクエスト/秒では足りません。同時開催の合計人数で計算し、公開ホストと外部DBで余裕を確認します。
- 429/503率、参照p95、DBのエラー/容量、未処理Webhook、匿名作成枠（全体100件/時）を確認します。IP由来の10件/時制限はプロキシのヘッダー処理に依存するため、ネットワーク側の制限も公開先で検討します。
- API障害ログの `requestId` / `code` / `status` で照合します。認証ヘッダー、復帰リンク、決済オブジェクト、ニックネーム、DB URLをログへ追加しないでください。アクセスログに機密クエリを残す設定も避けます。

## DB保全

公開環境のファイルDBは禁止しています。外部DBの自動バックアップ/PITRを有効にし、同じホストにしかコピーがない状態を避けます。最初の目安は復旧時点の欠損5分以内（RPO）、復旧60分以内（RTO）ですが、契約と復旧リハーサルで満たせた値を正式に記録してください。

アプリ単位の論理バックアップも作成できます。`.env.local` は安全な環境に置き、実際の接続値はコマンド引数に書きません。

```sh
npm run db:backup -- backups/pre-deploy.json
npm run db:restore -- backups/pre-deploy.json /tmp/bingo-restore.db
```

バックアップは一貫した読み取りスナップショットです。保存ファイルは新規作成のみ・権限0600、ディレクトリは新規作成時0700です。認証情報のハッシュや参加者情報を含むため、暗号化して別の保管先へコピーし、アクセスを制限してください。Gitには登録しません。論理コピーの周期をRPOと混同しないでください。

復元コマンドは**存在しないローカルファイル**にだけ書き込み、運用中DBを上書きしません。復元先でイベント数、カード、抽選済み番号、認証、決済記録を確認します。公開サービスの復旧ではDB提供元のPITR/新規DBへの復元を使い、検証後に接続先を切り替えます。本書のコマンドは公開DBへの切り替えを自動実行しません。

デプロイ前にバックアップを取り、`npm run db:setup` でスキーマを移行します。移行はトランザクションとバージョン番号で管理します。アプリより新しいスキーマは拒否するため、切り戻す場合は互換性と移行先を確認してください。

毎日一度、バックアップが正常なことを確認してから、別ジョブで以下を実行します。

```sh
npm run db:cleanup
```

利用期限から30日以上経過した部屋・カードと期限切れの作成制限を削除します。注文・決済記録は照合のため残ります。会計・プライバシーに沿う保存期間を運用開始時に定めてください。新規イベント作成からは清掃を実行しません。

## 障害時

1. `/api/health` と `/api/ready` を分けて確認し、公開ホストとDBの障害情報・直近の変更・エラーコードを確認します。キーや参加者情報は問い合わせへ添付しません。
2. 再接続中は幹事の抽選操作が無効になります。抽選結果が不明な場合は最新状態を確認し、DBを手で更新して抽選を進めないでください。
3. DBが復帰したら既存イベントでカードと抽選数を確認します。応答が失われても作成・参加のキー、抽選のゲーム番号と回数で重複を防ぎます。
4. データ損失の場合は新しいDBへ復元して検証します。参加者への案内と販売時の返金判断は担当者が行います。破損した運用DBへの上書きはしません。
5. 会場回線の断絶はモバイル回線や印刷済みカードで対応します。完全オフラインでのサーバー抽選、手動抽選結果の自動同期はありません。次回開催前に原因と復旧所要時間を記録します。

## 決済の照合

現在はsandboxのみ対応し、外部のStripe接続・実Webhookの試験は未完了です。liveキーとliveイベントは拒否します。連携の利用はユーザーの指定どおりsandboxの読み取りだけに限ります。

注文はStripe呼び出し前に保存します。Webhookは保存済みの注文ID・部屋・セッション・金額2,980円・JPYを照合し、同じ成功通知を重複処理しません。失敗通知が遅れても有料権限を下げず、別注文の遅延成功を記録しても有効期間は二重に延長しません。ブラウザの決済完了URLだけでは有効化しません。

支払済みなのに有効化されない場合は、sandboxのダッシュボードで該当注文の状態とWebhook配信を照合し、DB復帰後に該当通知を再送して確認します。`PAYMENT_MISMATCH` / `PAID_ROOM_MISSING` は手動の照合が必要です。複数注文が実際に成功した場合はすべて決済記録に残るため、担当者が確認します。返金は自動実行しません。将来の本販売では返金条件・窓口を公開し、実際の金銭操作には別途承認が必要です。
